# ADR-26a: مكان حفظ طابور المحرك وسياسة الاستئناف

| البند | القيمة |
|---|---|
| الحالة | **مقترح — بانتظار قرار المالك** (يحل محل الجزء التخزيني من ADR-26 «مقترح») |
| التاريخ | 2026-10-15 |
| المرجع | NFR-07 (ROADMAP §9)، `packages/engine/src/run.ts` (`RunQueueStore`)، ADR-26 (مستبدل بهذا وADR-26b)، `docs/DECLARED_LIMITS.md` (L-09) |

## السياق

مسار الخادم (`apps/server/src/routes/engine.ts`) لا يمرر `RunQueueStore`، فإعادة تشغيل الخادم تفقد الطابور — NFR-07 غير مستوفى إنتاجياً (الحد L-09). عقد المخزن المُنفّذ (P2-001/PR #147): `save` **قبل** أي تغيير في الحالة (إرسال: نمو؛ سحب: تقليص)؛ `load` مرة عند البناء وفشله يجهض البناء؛ الاستئناف at-least-once (انهيار بين السحب وتقليص الحفظ => إعادة تشغيل محفوظ فقط، لا فقد أبداً). المحرك **متزامن بالتصميم** (لا تداخل بين peek/save/pop) وطبقة التخزين المعتمدة في المشروع `node:sqlite` متزامنة.

## الخيارات

### الخيار 1 — SQLite بملف واحد (المقترح)
`IR_ENGINE_QUEUE_DB` (افتراضي `data/engine-queue.sqlite`)، جدول واحد `(run_id TEXT PRIMARY KEY, input TEXT NOT NULL, priority INTEGER, seq INTEGER)`، ترحيل `user_version` مثل مخزن القضية (ADR-04)، `PRAGMA synchronous=FULL`، تصريح الملف 0600.
- **لماذا:** معاملات ذرية لكل نمو/تقليص (يطابق عقد save-before-mutation حرفياً — النمط والتقليص كل منهما معاملة واحدة)؛ متزامن يطابق عقد المحرك؛ أداة فحص جاهزة (`sqlite3`)؛ خبرة قائمة في المشروع (مخزن القضية).
- **الأثر الأمني:** الطابور يحوي مدخلات التشغيل وقد تشمل بيانات أشخاص — 0600 + دليل بيانات الخادم (لا يُحمَّل أبداً إلى Git)؛ `validatePersistedRuns` (المُنفّذ) يرفض أي طابور مشوه قبل قبوله (فشل-مغلق)؛ لا يضيف سطح هجوم شبكي.

### الخيار 2 — سجل JSONL إضافي فقط (append-only) مع ضغط ذري
إلحاق سطر JSON لكل حدث (submit/pop)، وإعادة بناء الطابور من السجل عند الإقلاع، وضغط دوري (كتابة ملف مؤقت ثم rename ذري).
- **لماذا:** بلا قاعدة بيانات؛ الكتابة الإضافية رخيصة؛ الانهيار بين الحدثين لا يفسد السجل (سطر ناقص يُرفض عند التحميل).
- **الأثر الأمني:** نفس تصريح 0600؛ لكن الضغط نافذة فشو (انهيار أثناء الضغط يترك نسختين — يلزم منطق استرداد)؛ وترتيب السحب/الحفظ عبر سجل إضافي أضعف ضماناً من معاملة واحدة (يحتاج تسلسلاً صارماً للأحداث).

### الخيار 3 — ملف JSON ب كتابة ذرية (write-temp-then-rename) + قفل عمليات
أبسط الخيارات: كتابة الملف كاملاً إلى مؤقت ثم rename (ذري في POSIX) مع قفل ملف يمنع نسختين من الخادم.
- **لماذا:** أبسط تنفيذ؛ يعمل لأي حجم طابور عملي في نشر واحد.
- **الأثر الأمني:** لا معاملات — نسختان من الخادم على نفس الملف يتطلبان قفل ملف صحيحاً؛ وكل حفظ يعيد كتابة الملف كله (O(n) لكل حدث).

## التوصية

**الخيار 1 (SQLite)** — يطابق عقد المخزن المُنفّذ (متزامن، ذري لكل حدث)، ويوحد نمط التخزين مع مخزن القضية (ADR-04: node:sqlite)، ويجعل نقطة الفشل الوحيدة ملفاً واحداً قابلاً للفحص بسرعة، بلا منطق استرداد إضافي.

## سياسة الاستئناف (مشتركة بين الخيارات)

- تحميل عند البناء (المُنفّذ)؛ فشل التحميل يجهض إقلاع الخادم (فشل-مغلق — متسق مع سلوك البناء الحالي).
- الاستئناف at-least-once **معلن صراحة** في واجهة REST/OpenAPI («قد يُعاد تنفيذ تشغيل بعد إعادة تشغيل الخادم») — لا ادعاء exactly-once.
- **شرط سلوكي مطلوب قبل الادعاء بat-least-once إنتاجياً:** اختبار إعادة تشغيل حقيقي (عملية تُقتل بين السحب والتقليص وتُستأنف) يثبت إعادة التشغيل بلا فقد — النمط المحلي في `persistence.test.ts` لا يكفي.
- **لا يُنفَّذ التوصيل الإنتاجي قبل اعتماد ADR-26b** (مصدر purposeConfirmation عند الاستئناف) — بغض النظر عن اعتماد هذا القرار.
