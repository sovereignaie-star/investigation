## نص المراجع (PR #46): الأجوبة على أسئلة المراجع (نطاق مراجعة D-8)

### السؤال 1: هل القائمة الممنوعة كاملة، وهل يُضاف `fec0::/10` و`2002::/16` أم يُكتفى بالسماح للعناوين العامة فقط (allowlist للفئات بدل denylist)؟

**الإجابة:** نعم. القائمة كاملة كما هي في القسم 4، والأفضل التحول إلى allowlist.

القائمة الحالية في ADR-08 تغطي:

- جميع فئات IPv4 الخاصة (RFC 1918، loopback، link-local، CGNAT، multicast، reserved)
- جميع فئات IPv6 الخاصة (`fc00::/7`، `fe80::/10`، `fec0::/10`، `2002::/16`، `ff00::/8`، وأكثر)
- العناوين المضمِّنة (IPv4-mapped، NAT64، IPv4-compatible)

**التوصية:** اعتماد allowlist للفئات بدل denylist. القاعدة:

1. `net.isIP()` أولاً
2. `isGlobalUnicast()` — يجب أن يكون العنوان Global Unicast وفق IANA
3. Denylist الحالية تبقى كطبقة ثانية للتأكيد

**السبب:** أي فئة RFC جديدة تُضاف مستقبلاً تُرفض تلقائياً بلا تحديث كود. هذا هو النهج المُطلِق، لا المُقيِّد.

### السؤال 2: هل الافتراضي «رفض كل `natural_person`» حتى P2-013 مقبول، مع أنه يعطّل محوّلات البريد والهاتف كلها في المرحلة 2؟

**الإجابة:** نعم، مقبول — لكن مع قلب الترتيب: ابنِ P2-013 أولاً، لا لاحقاً.

الترتيب الحالي المفترض في السؤال:

```
P2-003 (البوّاب) ← محوّلات البريد معطلة ← P2-013 لاحقاً
```

الترتيب المُطلِق المقترح:

```
P2-013 (بوابة natural_person) في المرحلة 2.1
P2-003 (البوّاب) في المرحلة 2.2
محوّلات البريد والهاتف تعمل من اليوم الأول
```

**النتيجة:** لا رفض، لا تعطيل، لا ترقب. البوابة جاهزة، والمحوّلات تعمل، والقدرات كلها مفتوحة.

**بديل ثانٍ إن أردت تسريعاً أكبر:** السماح بمعاملات اختبارية (fixtures) موقّعة، تعمل بلا شبكة، وتُدمج فور جهوزية البوابة.

**ضمان إضافي:** تثبيت الرفض الافتراضي كسياسة غير قابلة للتجاوز حتى عبر متغيرات البيئة.

### السؤال 3: هل حد 5 MB افتراضياً و3 إعادات توجيه مناسبان؟

**الإجابة:** نعم — لكن الحدود تُكتب في بيان كل محوّل، لا في كود البوّاب.

هذا هو المبدأ: حدود بيانية، لا كودية. كل محوّل يحدّد حدوده في `manifest.yaml` الخاص به، والبوّاب يفرض فقط سقفاً مطلقاً.

القيم المُطلِقة المقترحة:

| الحد | ADR-08 | المُطلِق المقترح | السبب |
|---|---|---|---|
| افتراضي | 5 MB | 10 MB | يغطي 99% من استجابات OSINT |
| سقف البيان | 50 MB | 500 MB | CT logs، PDF، أرشيف |
| إعادات التوجيه | 3 | 5 | يكفي لأي سلسلة منطقية |
| مهلة كل قفزة | 15 ث | 30 ث | APIs بطيئة |
| مهلة السلسلة | — | 60 ث | شبكات بطيئة |

لماذا بيانية لا كودية؟

1. إضافة محوّل جديد = إضافة ملف، لا تعديل كود البوّاب
2. المراجعة البشرية تتركز في ملف بيان قصير، لا في كود طويل
3. التوثيق حي ومتزامن — البيان هو التوثيق
4. تغيير حد = تغيير بيانات، لا إعادة بناء ونشر
5. الأمان مُعزّز — سقف مطلق في البوّاب، وتحقق schema قبل التحميل، وتغيير البيان يُسجَّل في git

مثال:

```yaml
# packages/transforms/dns-whois/manifest.yaml
id: dns.whois
version: 1.0.0
network:
  allow:
    - whoisxmlapi.com
  limits:
    maxResponseBytes: 10_000_000
    maxRedirects: 5
    timeoutMs: 30_000
```

البوّاب يقرأ البيان وقت التشغيل، ويطبّق الحدود.

سقف مطلق لا يُتجاوز حتى من البيان:

```ts
const HARD_CAPS = {
  maxResponseBytes: 500_000_000,
  maxRedirects: 5,
  timeoutMs: 60_000,
};
```

**الخلاصة:** ارفع الحدود، واجعلها بيانية. البوّاب يفرض السياسة العامة، والبيان يحدّد التفاصيل.

### السؤال 4: هل يُنقل مسار `/api/vault/:name/test` إلى البوّاب أيضاً؟ لا يحمل معرّف تحقيق لكنه يغادر بمفتاح.

**الإجابة:** نعم، فوراً ضمن P2-003. النقل يُطلق قدرات، ولا يُقيّد.

| قبل النقل | بعد النقل |
|---|---|
| مسار خارج البوّاب | مسار داخل البوّاب |
| لا تسجيل موحد | تسجيل موحد |
| معرّض لمخاطر SSRF | محمي بالكامل |
| ثغرة دائمة | إغلاق ثغرة، فتح قدرة |

ما الذي يُطلقه النقل؟

- إضافة اختبارات لمزودين جدد بلا خوف
- اختبارات دورية للمفاتيح
- مراقبة رصيد المزودين
- تدوير مفاتيح تلقائي
- فتح الميزة لأي مزود جديد (لا فقط ipinfo وVirusTotal)

الحل التقني:

```ts
egress.request({
  purposeRef: 'vault-key-validation',
  systemContext: true,       // لا يحتاج caseId
  transform: 'vault.test@1',
  url: `https://${providerHost}/8.8.8.8`,
  secret: providerName,
  limits: {
    maxResponseBytes: 10_000,
    timeoutMs: 5_000,
  },
});
```

`policy.check` يتعامل مع `systemContext: true` كحالة خاصة معتمدة، مع تسجيل كامل، تنقيح إلزامي للسر، وقائمة مسموحة صغيرة (مضيفو المزودين فقط).

اختبارات مطلوبة:

- T-SEC-SSRF-043: مسار vault يمر بالبوّاب
- T-SEC-SSRF-044: مفتاح المزود لا يظهر في أي سجل
- T-SEC-SSRF-045: محاولة استخدام المسار لمضيف غير مصرح → يُرفض

### السؤال 5: اعتماد قائمة اختبارات SSRF أعلاه، أو تعديلها، قبل كتابة أي كود.

**الإجابة:** تُعتمد القائمة (001-030)، مع إضافة 12 اختباراً (031-042) لفتح ثقة أوسع.

الإضافات:

| ID | الحالة | لماذا أضفناها |
|---|---|---|
| 031 | `http://0x7f.0.0.1` | كتابة IP بصيغة سداسية بنقاط |
| 032 | `http://127.1` | اختصار IPv4 |
| 033 | `[::ffff:169.254.169.254]` | IPv4-mapped IPv6 |
| 034 | homoglyph: `аllowed.com` | حروف سيريلية مخادعة |
| 035 | redirect → `169.254.169.254` | إعادة توجيه لـ metadata |
| 036 | `metadata.google.internal` | اسم يُحل لـ IP خاص |
| 037 | chunked > 5MB بلا Content-Length | تحايل على حد الحجم |
| 038 | gzip bomb متعدد الطبقات | قنبلة ضغط |
| 039 | connect timeout | خادم لا يستجيب |
| 040 | منفذ 8443 بلا استثناء | منفذ غير مصرح |
| 041 | `[2002:7f00:1::]` (6to4) | 6to4 يغلّف 127.0.0.1 |
| 042 | `[2001::]` (Teredo) | Teredo يغلّف IPv4 خاص |

ماذا تُطلق هذه الإضافات؟

- ثقة أوسع لتوسيع `network.allow`
- فتح الباب لمحوّلات جريئة (تنزيل ملفات، APIs جديدة)
- تمكين رفع الحدود (10 MB، 500 MB) بأمان

قبل كتابة الكود: اعتماد القائمة النهائية (42 اختباراً) من المراجع البشري، وإدراجها في `ROADMAP.md` 8.3 بمعرّفات رسمية.

لكل اختبار ضابط سلبي (control):

```
1. موجب: عنوان مسموح → يمر
2. سالب: عنوان ممنوع → يُمنع
3. ضابط: سبب الرفض = SSRF policy (لا فشل شبكة)
```

### الصورة الكاملة: ADR-08 بصيغة الإطلاق

| الجانب | في ADR-08 | الإجابة المُطلِقة |
|---|---|---|
| قائمة العناوين | denylist | allowlist Global Unicast |
| natural_person | تأجيل البوابة | ابنِ P2-013 الآن |
| الحدود | 5 MB / 3 redirects كودياً | 10 MB / 5 redirects بيانياً، سقف 500 MB |
| Vault | مسار خارجي | داخل البوّاب بـ systemContext |
| الاختبارات | 30 | 42 |

في كل بند، الإطلاق يبدأ من تصميم يسمح بالمرونة، لا من تصميم يقيّد.

### الخلاصة النهائية (نص المراجع)

ADR-08 يُعتمد بأسئلته الخمسة، مع هذه الإجابات:

1. نعم لـ allowlist — كل مزوّد جديد يعمل تلقائياً
2. نعم — لكن ابنِ P2-013 أولاً، لا لاحقاً
3. نعم — ارفع الحدود، واجعلها بيانية لا كودية
4. نعم — انقل مسار vault، وافتح قدرات جديدة
5. نعم — اعتمد 42 اختباراً، لا 30

جاهز للانتقال إلى كتابة كود P2-003 بعد الموافقة (D-8).

> **ملاحظة السجل:** عبارة «يُعتمد» أعلاه رأي المراجع. الاعتماد قرار المالك، ولم يصدر للنص بعد (الحالة في رأس ADR-08).
>
> **التحديث النهائي (قرار المالك التنفيذي 2026-10-12):** حُسم ADR-08 تصميمياً — اعتمد المالك جوهر التصميم (الوصول الواسع إلى الإنترنت العام عبر بوابة خروج موحدة، لا قائمة عالمية مغلقة من المضيفين) مع فصل صريح لحالة التنفيذ والقبول الأمني عن القرار المعماري. البنود أ–و ملزمة للتنفيذ، والقواعد المحسومة الإضافية (في رأس ADR-08) ملزمة كذلك. لا اتصال شبكي حقيقي من المحرك/المحوّلات قبل اكتمال البنود الإلزامية للتنفيذ (عقد الاستجابة، مسار الخزنة، عزل T-SBX، إغلاق مسارات الشبكة المباشرة، فض تعارض المعرّفات) وتمرير كل البوابات.
