# ADR-04: قضية = مجلد فيه SQLite عبر `node:sqlite` ومجلد blobs، وPostgres لنشر الفرق لاحقاً

| البند | القيمة |
|---|---|
| الحالة | مُقرّر بتفويض ومُنفّذ (P1-013، P1-014) |
| التاريخ | 2026-10-10 |
| المرجع | `docs/ROADMAP.md` 5.9، 5.5؛ `packages/store` |

## السياق

القضية يجب أن تكون محمولة، وسهلة النسخ الاحتياطي والحذف، وقابلة للتحقق دون اتصال، وأن تعمل كما هي على جهاز محلي وفي Docker وعلى Render وRailway (P1-024). الاقتراح الأول في 5.9 كان `better-sqlite3` مع SQLCipher، وهي وحدة أصلية تحتاج بناءً أو ملفات مسبقة البناء لكل منصة وإصدار Node.

## القرار

| الجانب | القرار |
|---|---|
| المحرك | `node:sqlite` المدمج في Node 24 (SQLite 3.53؛ مستوى الاستقرار 1.2، مرشح إصدار، بلا علم تشغيل). لا وحدات أصلية ولا أدوات بناء في الصورة |
| التخطيط | مجلد لكل قضية: `case.sqlite` (الوصف والسلسلة والتدقيق وفهرس الأدلة) و`blobs/` (الأدلة الخام، P1-010) |
| الإعدادات | `journal_mode = WAL`، `synchronous = FULL`، قيود المفاتيح الأجنبية مفعّلة، مهلة انشغال 5 ثوانٍ، جداول `STRICT` |
| الإضافة فقط | `ledger` و`audit_events` و`evidence` ترفض UPDATE وDELETE بمشغّلات (triggers) في القاعدة نفسها، ومع ذلك تُتحقق السلسلة عند كل فتح، فالتعديل بعد حذف المشغّلات يُرفض أيضاً |
| الترحيلات | قائمة مرقّمة غير قابلة للتعديل بعد الإصدار؛ كل ترحيل في معاملة؛ الإصدار في `PRAGMA user_version`، وبصمة SQL كل ترحيل في `schema_migrations`. تُرفض قاعدة من إصدار أحدث (`newer`)، وترحيل عُدّل بعد تطبيقه (`drift`)، وفجوة في الترقيم (`gap`)، ويُتراجع عن الترحيل الفاشل كاملاً |
| التجريد | `LedgerStore` و`BlobStore` واجهتان؛ يمكن تبديل المحرك (`better-sqlite3`) دون تغيير السلسلة |
| التشفير | ليس في `node:sqlite` دعم SQLCipher، فالتشفير على مستوى التطبيق في P1-014 (حمولات السلسلة والأدلة بـ AES-256-GCM ومفتاح مشتق من عبارة مرور) |
| الفرق | Postgres عبر Drizzle (`lib/db`) لنشر الفرق لاحقاً (ADR-11) |

## البدائل

`better-sqlite3` مع SQLCipher (وحدة أصلية، وبناء لكل منصة، وتعقيد في Docker والاستضافة)؛ IndexedDB/Dexie في المتصفح (D-035: بلا ترحيلات ولا تشفير، وحصة محدودة)؛ ملفات JSON (بلا معاملات ولا قيود).

## العواقب

لا اعتماد أصلي، فالصورة نفسها تعمل على أي منصة. `node:sqlite` ما زال مرشح إصدار: يُثبَّت Node 24 في CI وDocker، ويُراجع عند كل ترقية لـ Node. التشفير يغطي الحمولات لا بنية الجداول (الأنواع والأوقات تبقى مقروءة)، وهذا مقبول لأن الحمولات هي المحتوى الحساس.

## التشفير (P1-014، مُنفّذ)

| البند | القرار |
|---|---|
| مفتاح القضية | 256 بت عشوائي لكل قضية، مغلّف بـ AES-256-GCM تحت مفتاح مشتق من عبارة المرور بـ Argon2id (`node:crypto` المدمج منذ Node 24.7، ومطابق لمتجه RFC 9106 §5.3). الكلفة الافتراضية هي التوصية الثانية في RFC 9106: 64 MiB، و3 مرات، و4 مسارات |
| الملف | `case.key.json` بإذن 0600 بجانب `case.sqlite`، صيغة `ir-casekey/1`، ومربوط بمعرّف القضية (يُرفض ملف مفتاح قضية أخرى) |
| المفاتيح الفرعية | HKDF-SHA256 من مفتاح القضية: للحمولات، وللأدلة، ولعناوين الأدلة |
| الحمولات | كل حمولة في السلسلة عدا `checkpoint` تُخزّن ظرفاً `aes-256-gcm/1` (iv، ct، tag) وAAD = معرّف القضية + النوع. السلسلة تجزّئ الظرف، فـ `ir verify` يتحقق من السلسلة والتواقيع بلا عبارة المرور |
| الأدلة | zstd ثم AES-256-GCM (AAD = معرّف القضية + SHA-256)، والعنوان على القرص HMAC للبصمة، فأسماء الملفات لا تكشف أي وثيقة معروفة تحويها القضية. `Evidence.blobRef` يبقى العنوان المنطقي |
| تغيير عبارة المرور | `changePassphrase` يعيد تغليف المفتاح نفسه فقط، دون إعادة تشفير المحتوى |
| القضايا غير المشفرة | ممكنة صراحة (بلا عبارة مرور)، ويُسجّل `meta.encryption` القيمة `none` |
| الظاهر بلا مفتاح | أنواع المدخلات، والأوقات، والفاعل، وحجم الأدلة ونوع MIME في الفهرس. المحتوى والبصمات الحقيقية مخفية |
